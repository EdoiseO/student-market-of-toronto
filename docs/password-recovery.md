# Browser-bound password recovery

Recovery uses the installed Supabase PKCE flow and a server-held, single-use intent. It never stores recovery Auth tokens in browser cookies, localStorage, or the database. A separate HttpOnly cookie binds the initiating browser to each intent; the intent records the requested email and the recovery-purpose verifier generated by the SDK. Multiple requests have separate verifiers. The existing marketplace session is not the recovery credential.

1. `POST /api/auth/recovery` with `action: request` requires same-origin JSON, reserves a rate-limited intent, calls `resetPasswordForEmail` in an isolated in-memory client, and stores its verifier. Responses do not distinguish missing accounts from rate-limited addresses.
2. The email opens `/reset-password?state=<intent>&code=<PKCE code>`. GET does not redeem the code. The page removes query/fragment material from history and reads the intended email only when its browser binding matches. It holds the code in memory, so reloading the cleaned page requires another email. A link can also be reopened from the email while its code and intent remain unused.
3. The user sees the intended account and submits the new password and confirmation. Same-origin JSON POST atomically consumes the matching, unexpired intent before exchanging the code in an isolated client. A verified Auth user must match the recorded email. No ordinary browser session is adopted.
4. Confirmed password updates trigger global refresh-session revocation. A failed revocation is reported separately from the successful password change. Existing access JWTs can remain valid until expiry. Only an ordinary session belonging to the recovered account is cleared; another account remains signed in. Ambiguous updates require checking the new password or requesting a new link, never replaying the consumed intent.

## Required release configuration

- Apply `20260906150000_browser_bound_password_recovery.sql` before deploying the application change. The table and reserve/claim RPCs are service-role-only; authenticated/anonymous clients have no direct access. The existing `SUPABASE_SERVICE_ROLE_KEY`, public Supabase URL and publishable key must be configured on the server.
- In the Supabase Auth redirect allowlist, permit the exact deployed `/auth/callback` URL for new registration confirmations and the deployed `/reset-password` route with its `state` query parameter (for example `https://your-host/reset-password?state=*`). Use the actual canonical origin, and verify the project's glob matching in an isolated Auth environment before release. Add separate local/test origins only where appropriate.
- The recovery email must use Supabase's `{{ .ConfirmationURL }}` verification URL so its PKCE verification redirects to the supplied `redirectTo`. A custom template that constructs a raw token, `token_hash`, or an unrelated site-root URL is incompatible. Do not add a compatibility fallback. New signup requests explicitly set `emailRedirectTo` to `/auth/callback`; signup confirmation templates must also respect that redirect.
- Browser clients intentionally use `detectSessionInUrl: false`. The registration callback owns ordinary PKCE session exchange; it checks failure, stages cookie writes, rejects recovery-purpose verifiers and preserves an already-signed-in account.
- Complete recovery within five minutes of requesting the email. Hosted verification confirmed that Supabase's current recovery PKCE flow expires five minutes after the request; clicking the email does not restart that clock. The application intent and browser-binding cookie retain their 15-minute lifetime as an upper bound, which does not extend provider validity. The earlier deadline wins. This follows the provider's [five-minute default](https://github.com/supabase/auth/blob/master/internal/conf/configuration.go) and [recovery flow expiry calculation](https://github.com/supabase/auth/blob/master/internal/models/flow_state.go).
- Sending is limited to one request per address per minute, five per address per hour and twenty per bound browser per hour, in addition to Auth provider limits. The next request prunes records older than one day. Configure provider mail limits/captcha as needed; do not log recovery request bodies, code-bearing URLs or PKCE verifiers.
- Cross-device recovery uses **Request another reset email** in the device/browser where the user wants to finish. There is no transferable token/OTP fallback and no new email-template secret to expose.

## Verification

`node --test tests/password-recovery.test.mjs` exercises the real installed Supabase SDK against a local fetch fixture: PKCE challenge/verifier consistency, intended identity, token/hash rejection, invalid verifier, replay, password rejection, ambiguous responses and revocation failure. Native disposable PostgreSQL verifies grants, expiry, binding, rate limits and concurrent one-use claims. No remote Auth calls are made by these tests.

Before release, also verify delivery/allowlist/template behavior using isolated Auth accounts, the English/French form states, no mutation on mail-scanner GET, existing same/different account cookies, blocked/name-restricted accounts, and the normal signup confirmation flow. Local unit/provider fixtures cannot verify remote email settings. No production configuration is changed by this implementation.
